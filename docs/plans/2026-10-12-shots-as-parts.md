## Intent

- Problem: A code-only reel is one `index.html` holding every scene, so changing one shot means rebuilding and re-versioning the whole reel. Nothing can be adjusted on its own.
- Why: Review happens shot by shot. A fix to "The hook" should not touch, re-freeze or risk the eleven shots after it.
- Proposed outcome: Each shot has its own page and its own history. You or the agent change one shot and the rest of the reel stays exactly as it was. The reel remains one deliverable: the shots in order, one sound mix across them, one timeline, one render.
- Affected: the timing contract (ADR 0001) and `server/core/_internal/contract.ts`, version reading and building, comment pins and their carry, comment batches, the stage and player in `web/src`, the Storyboard, the render path (`skill/kinotta/scripts/render.js`), `skill/kinotta` (how the agent builds and answers), `CONTEXT.md` (Shot, Scene, Version, Comment batch), a new ADR.
- Constraints: Builds on `2026-10-12-live-edits-freeze-at-render.md`, which lands first. Music and sound effects keep running across shots. Existing single-page reels keep opening and rendering. A shot stays inside its reel; it is not a separate reel.
- Out of scope: Reusing a shot in another reel. Sections as the unit (they stay a grouping). Parallel agent builds of several shots.
- Open questions: all settled with the owner in the 2026-10-13 grilling session.
  - O1: settled. When a shot changes length, later shots move, because shots are an ordered sequence. Sound moves only if it is attached to a shot that moved.
  - O2: settled. One comment batch per hand-off, grouped by shot, naming the shots it covers. The agent rebuilds only those.
  - O3: settled. Code-built reels only. Footage reels are unchanged.
  - O4: settled. Not in the first build. A shot animates its own entrance and exit inside its own time. A transition that needs two shots on screen at once is a known gap.
  - O5: settled. Existing single-page reels are left alone and keep opening and rendering. New reels are built as parts. The skill converts an old reel only when asked.
  - Also settled: a version is a list saying which revision of each shot it uses, and an unchanged shot is not copied. A shot is identified by a fixed name; its number is only its position. Fonts, brand colours and shared styles live in one shared folder, and a change there counts as a change to every shot.

## Goal

A code-built reel can be built as parts: each shot is its own folder of immutable revisions, and a version is a manifest naming one revision per shot plus the shared styles. Building a version that changes one shot writes one new shot revision and one manifest. Everything downstream of a version (the stage, stills, pins, `kinotta check`, renders) keeps working, because each version still holds one assembled `index.html` that keeps the timing contract.

Acceptance criteria:

- A parts reel with twelve shots where the agent changes shot 04 gains exactly one new folder under `shots/` and one new `v<n>`. The other eleven shots' files are byte-identical and are not copied.
- `v<n>/index.html` of a parts version is generated by Kinotta from the manifest, never written by hand, and passes the same contract checks as a single-page version. Assembling the same manifest twice gives the same bytes.
- A shot keeps its name when shots are added, removed or reordered. Its number is its position in the manifest. Pins, carry and history follow the name.
- Changing a shot's duration in the manifest moves every later shot's start. Sound placements move only when attached to a shot that moved.
- A change to the shared folder is reported as changing every shot, in `changedSections` and in the editor.
- A comment batch from a parts reel is grouped by shot and begins with a line naming the shots to rebuild.
- `kinotta build <reel>` assembles the next version from a manifest the agent wrote and prints the same issues `kinotta check` would. `kinotta check` reports a manifest that names a missing shot revision.
- Every existing single-page reel opens, checks and renders with no change to its files.

## Approach

The outcome is one file and one history per shot. The lowest-risk way to get it is to keep the single assembled page that every other part of Kinotta already reads, and to generate that page from per-shot files. Nothing in the stage, the render script or element pinning then has to change.

An alternative was considered and rejected: one iframe per shot inside a host page. Renders load pages from `file://`, where each file is its own origin, so the host could not call a shot frame's `seek`. Element pinning (`web/src/stage/_internal/dom.ts`) also reads one document with `elementFromPoint`, and would need to reach into nested frames.

Layout on disk for a parts reel:

```
reels/<reel>/
  shots/<name>/r<k>/        shot.html, shot.css, shot.js, assets/   (one immutable revision)
  shared/r<k>/              shared.css, fonts/, assets/             (one immutable revision)
  v<n>/shots.json           the manifest, contract 2
  v<n>/index.html           assembled from the manifest
```

- A shot revision is a fragment, not a whole page: `shot.html` holds one root `<section data-scene="<name>">` with its named `data-el` elements; `shot.css` has every rule scoped under `[data-scene="<name>"]`; `shot.js` is a module that exports `seek(local)`, where `local` is seconds from the shot's own start. A revision folder is never edited after it is written.
- The manifest is `shots.json` with `"contract": 2`: `duration`, `shared` (a revision id), and `shots` in play order, each `{ name, revision, duration, title, description }`. Starts are not stored; they are the running sum of the durations before. `scene` equals `name`, so existing code that matches shots to scenes keeps working.
- The assembler is a pure function in `server/core/_internal` from a manifest and the revision folders to one HTML string: the shared styles, then each shot's markup with `data-start` and `data-duration` filled in from the manifest, its styles, and a small runtime that defines the global `seek(t)`, activates the scene playing at `t` and calls that shot's `seek(t - start)`. Its output keeps contract 1, so `scanPage`, the stage and `render.js` read it as they read any version page.
- `readVersion` accepts contract 2: it reads shots from the manifest, computes starts, and exposes each shot's `name` and `revision`. Contract 1 versions take the existing path untouched.
- Publishing a parts version goes through the existing stage-and-rename in `version-build.ts`: write the manifest, assemble `index.html`, run the contract checks, rename into place. `kinotta build` is the CLI entry for the agent. After live edits, a freeze that changes only timing or which revision a shot uses writes a manifest and an assembled page and no shot folders.
- Change detection compares manifests: a shot is changed when its revision differs, moved when only its start differs, and every shot is changed when `shared` differs. This replaces page-markup comparison for parts versions only.
- Carry and pins use the shot name. A pin's `shot` stays the displayed number for the version it was made on, and a new `shotName` field is what carry follows. Comments on single-page versions carry by number and time as now.
- The owner's element offsets stay version-level edits applied to the assembled page (`kinotta-edits.css`), so moving an element does not create a shot revision.
- `batch.ts` groups a parts reel's comments under shot headings and adds a `Rebuild:` line naming the shots that have comments.
- The skill (`SKILL.md`, `reference/contract.md`) learns the parts layout: write a new `r<k>` only for shots the batch names, copy the manifest forward, run `kinotta build`. A new ADR records the manifest and the assembler; `CONTEXT.md` gains Revision and updates Shot and Version.

## Steps

Each step is a failing test first, then the change.

1. Manifest reading and validation for contract 2 in `contract.ts` and `version.ts`, with computed starts. Single-page fixtures stay green.
2. The assembler, with a determinism test and a test that its output passes `scanPage` and `checkShotsAgainstPage`.
3. Publishing a parts version through stage-and-rename, and `kinotta build`.
4. `kinotta check` and the render gate on a parts version, including a missing revision. A browser test that the stage plays and pins an assembled page.
5. Change detection from manifests, including a shared-folder change.
6. `shotName` on pins and carry across an added, removed and reordered shot.
7. Batches grouped by shot with the `Rebuild:` line.
8. A render test of a parts version at Draft, to prove `render.js` needs no change.
9. Skill references, the ADR, `CONTEXT.md` and `server/core/README.md`.

## Risks

- This design was written from reading the code, not prototyped. Step 2 is the proof; if an assembled page cannot keep contract 1 for a real reel, stop and report before building on it.
- Shots share one document, so one shot's CSS or script can leak into another. The assembler must reject a `shot.css` rule that is not scoped under its own scene, and shot scripts must be modules with no globals.
- The existing code-only Save rewrites scene timing inside `index.html`. For a parts version timing lives in the manifest, so that path must write the manifest and reassemble, not patch the page.
- Carry by name and carry by number will coexist. A reel that is converted from single-page to parts crosses from one to the other in one version; the scene name is the bridge.
- Live edits lands first and changes Save into a freeze. This plan is written against the behaviour that plan describes, not the code as it is today.

## Checks to run

- `npm run typecheck`, `npm run build`.
- Vitest, one worker: the new manifest, assembler, publish, change-detection, carry and batch tests, plus the existing contract, version, carry, comment-batch, save and render-queue suites.
- Playwright, one worker: `storyboard`, `pins`, `review` and `renders` specs against a parts fixture reel and against the existing single-page fixtures.
- `kinotta check reels/kinotta-showcase` still reports what it reported before. No edit operations on that reel.
