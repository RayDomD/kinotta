## Priority findings

### P2: The alternate sheet's desktop capture needs more height than the original viewport

**Location:** `web/src/styles.css:242`, `:413–414`; `tests/e2e/alternates.spec.ts:122`, `:135–140`; captured `tests/artifacts/alternates/sheet-{dark,light}-1600.png`. Category: responsive layout / implementation integrity.

**Measured artifact/source evidence:** Both desktop sheet PNGs are **900×1000px**. The test starts with a **1600×1000px** viewport, checks horizontal bounds only, then deliberately expands the viewport to `max(1000, ceil(bounds.height + 96))` before taking an element screenshot. CSS reserves 52px for the top bar and 16px scrim padding at each end, leaving **916px** for a sheet in the original viewport. A 1000px-tall sheet requires roughly **84px** more than that space. The 900px width cap has already been reached, so increasing viewport height for capture does not reduce its rendered contents. This is geometry inferred from captured element dimensions and current CSS, not a newly measured scroll position.

**Impact:** The comparison thumbnails and action/pinning rows force vertical scrolling in a large-monitor 1000px-high session despite DESIGN's requirement that frame, chips, words and hint fit without scrolling. An element screenshot that expands its viewport hides this fit problem from a casual review.

**Recommendation:** Budget the frame against the actual remaining height after alternate thumbnails and controls, or compact those secondary rows, while keeping the frame large enough to judge. Add a real vertical-fit assertion at the original viewport height if this is fixed; keep full-sheet captures as supplementary evidence.

Suggested command: `$impeccable adapt` or `$impeccable layout`.

### P2: Actual typography-role drift is buried under generic size advisories

**Location:** `web/src/styles.css:303` (`.line`), `:384` (`.c p`), `:410` (`.note-read`), `:268` (`.alternate-preview p`); `web/src/review/review.css:278` (library paths/effect descriptions), `:271` (library filter tabs). Category: implementation integrity / accessibility.

**Verified source:** Reading/comment/note copy uses 14px where DESIGN specifically prescribes Body 15px. Library path/description metadata is 10px, below the explicit 11px Review floor; media filter tabs use 11px versus the more specific 13–14px tool/tab role. By contrast, 11px native clip labels and 14px Review tabs are explicitly permitted. The `.rv-who` advisory is overridden to 12px in the actual Versions rail (`styles.css:597`), so the Working note is compliant with its specific 12–13px role.

**Impact:** Real text-role differences can make comments and descriptions harder to read and the media rail more cramped. **Recommendation:** Reconcile the small set of true role mismatches with DESIGN. The accepted older alternates mockup uses 14px comment text, so resolve that conflict deliberately instead of letting a detector choose. Preserve 15px Body and documented 11–14px Review/10–14px numeral roles. The complete occurrence-by-occurrence decision is in [font-disposition.md](font-disposition.md).

Suggested command: `$impeccable typeset` for a future focused pass.

### P2: Tab roles do not implement a tab keyboard contract

**Location:** `web/src/review/_internal/EditsPanel.tsx:134` onward; `EditorRail.tsx:14` onward; `MediaLibrary.tsx:46` (media filters). Category: accessibility / implementation integrity.

**Verified source:** Tablist/tab roles and `aria-selected` exist, but tab buttons all remain in normal Tab order, have no local arrow/Home/End handling, and do not associate controlled content via `aria-controls`/labelled tabpanels. The rail also permits both roles to be unselected when collapsed. Review's global key handler intentionally excludes only Space on a focused button (`Review.tsx:72` onward), so navigation keys do not acquire tab-switching behavior simply by focusing these controls.

**Impact:** A keyboard or screen-reader user encounters a tab interface with button-like navigation. Tab/Enter still offers a workaround, but expected left/right tab selection and clear content association are absent. This is a source-supported interaction-contract gap; no assistive-technology behavior is claimed to have been tested.

**Recommendation:** Either complete the tab pattern with explicit focus/selection/content relationships, including the collapsible rail state, or use ordinary labelled toggle buttons where that is the intended interaction. Keep playback shortcuts from consuming tab-navigation keys.

Suggested command: `$impeccable harden`.

### P2: Audio envelope sliders are nested inside a selectable button

**Location:** `web/src/review/_internal/NativeLanes.tsx:247` wraps the entire clip; `:265` adds focusable SVG circles with `role="slider"` inside that button. Category: accessibility.

**Verified source:** Each audio clip is one native `<button>` and its envelope points are focusable slider descendants with their own keyboard handler, names and values. These are independently interactive descendants of a native button. Point values are keyboard adjustable in code; point creation currently uses a waveform double-click (`:258` onward).

**Impact:** The composite control has conflicting semantics and can be flattened or inconsistently exposed in accessibility trees. A keyboard-only creation path for an envelope point is not evident in this control. The actual accessibility-tree result, point focus and alternative Clip inspector paths require a populated audio fixture/browser pass before any stronger WCAG claim.

**Recommendation:** Put the clip selection button and independently interactive envelope controls alongside each other in a noninteractive positioned container, retaining the same visuals. Verify keyboard creation/edit/removal in the Clip inspector or add a clear equivalent path.

Suggested command: `$impeccable harden`. This is an adjacent Review audio path, not a proven defect in the supplied code-only Parts fixture.

### P2: Timeline pin identity diverges from the editor's signature pin system

**Location:** `web/src/review/review.css:256`, `:366`; `web/src/review/_internal/MediaEditor.tsx:552`. Category: implementation integrity.

**Verified source:** `.editorial-pin` is a 24px circle (`border-radius:50%`) with inherited Outfit 11px. The button renders the identifying pin number directly and has no `.dot`/Doto rule. DESIGN requires zero radius, the hex pin silhouette and Doto for identifying/measuring numbers. The 11px size is valid; the detector size advisory is not the actual problem.

**Impact:** The same comment number changes its visual identity between the frame/Storyboard and Review ruler, weakening the cross-surface cue the signature pin system is meant to provide.

**Recommendation:** Reuse the established hex/Doto vocabulary on the ruler while preserving the button's accessible name and seek action. Do not enlarge the number solely because it is below 16px.

Suggested command: `$impeccable polish`.

### P3: Warning colors bypass the theme token system

**Location:** `web/src/review/review.css:257` and `:333`. Category: theming / implementation integrity.

**Verified source:** Attachment-broken border and overload tint/border repeat literal `oklch(.65 .19 30)` values. The detector reports three occurrences because line 333 has both translucent background and border values.

**Impact:** These error states cannot be calibrated for light/dark through the theme system. Their use is functionally justified as warnings, so they are not decorative violations of the One Light Rule. Actual state visibility/contrast needs runtime evidence.

**Recommendation:** Introduce one semantic warning token with theme-appropriate values if these states need correction; retain text/shape equivalents (e.g. Reattach and overload notices). No warning-token refactor was performed.

Suggested command: `$impeccable colorize`, then `$impeccable polish` after any authorized corrections.
